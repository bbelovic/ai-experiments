The concept: a tool is a contract

For this operation, the contract includes a name, a description, input fields, validation, a structured result, and failure behavior. Spring AI can turn an @Tool-annotated method into a ToolCallback. A description helps a model select the operation; application code must still enforce its rules. See Spring AI: Tool Calling.

JSON arguments
  → local Spring AI ToolCallback
  → FinancialStatementRequest(ticker, annualPeriods)
  → getFinancialStatements(request)
  → validate tool limit, delegate to injected loader
  → FinancialStatements serialized as a tool result

No model selects the tool in this exercise. We supply the JSON ourselves to isolate conversion and execution. The callback is also not an MCP server; that protocol boundary comes next.

Checkpoint A: make the Java contract testable

Following our Spring IoC discussion, Codex refactored the APIs to use FinancialStatementRequest. The tool now receives a FinancialDataLoader through its constructor. The loader keeps the three statement services as explicit constructor dependencies. Request-specific inputs travel through operation methods; no custom factory is required.

Current API shape
FinancialStatements getFinancialStatements(FinancialStatementRequest request)
FinancialStatements load(FinancialStatementRequest request)
FinancialStatements annualBalanceSheetStatement(FinancialStatementRequest request)
// The income and cash-flow service methods take the same request.

A test loader can be request -> TEST_FIXTURE. Capture or assert its request to verify delegation. No Spring context is needed for these tests.

The request's compact constructor rejects null/blank tickers and nonpositive period counts and normalizes the ticker. The tool rejects a missing request and applies the tool-specific maximum of four periods. General service callers can request more. Stable configuration such as User-Agent remains a constructor dependency of the services; external Spring wiring is later work.

Checkpoint B: describe and invoke the same contract

Continue after A is working. Add org.springframework.ai:spring-ai-model:2.0.0 to ai-tooling/pom.xml: this matches the AI BOM currently used by chat-client. For this single dependency, an explicit version is enough; no model-provider starter or Boot migration is needed in tooling. The earlier lesson's 2.0.2 reference is not a reason to mix versions now.

In the tooling module's properties, enable maven.compiler.parameters=true so reflection can retain the method parameter name request. Add @Tool to the operation and @ToolParam descriptions to the request parameter and relevant record components. Keep provider configuration and credentials outside the record.

Annotation imports and description checklist
import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.tool.annotation.ToolParam;

Write the descriptions yourself. Include: annual statements; ticker input; period bound; fewer periods possible; formatted value strings; null for unavailable facts. A numeric description is not executable range validation. Keep the runtime checks from A.

Use ToolCallbacks.from(tool) in a local test to create the callback. For this method-based tool, inspect the generated outer request object and its nested ticker and annualPeriods fields; verify required fields. Invoke it using the matching nested JSON and parse its returned JSON to verify null and zero remain distinct.

Small callback inspection hint
import org.springframework.ai.support.ToolCallbacks;

The API signatures were checked against the locally installed Spring AI 2.0.0 JAR. Your injected fixture loader makes this execution deterministic without a model or SEC request.

Add one callback test with invalid record data, such as a blank ticker: deserialization constructs the record and runs its compact constructor. The callback may wrap validation failures; inspect the cause instead of assuming the exception type from a direct Java call. An explicit assertion that the loader is not invoked can clarify the boundary. A callback case with annualPeriods=5 is optional because the tool-specific range rule already has direct Java coverage; do not repeat the whole validation matrix here.

We keep failures explicit in these local tests. Translating expected failures into client-facing tool responses belongs to the later MCP/application adapter; do not catch every exception and return an empty success object.
