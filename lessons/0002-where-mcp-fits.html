A protocol boundary

MCP standardizes communication between applications providing capabilities and applications consuming them. The host is the AI application; it manages an MCP client communicating with an MCP server. A server can expose tools, resources, and prompts. The protocol does not dictate the host's model reasoning. See the official MCP architecture.

Assistant application (host)
  |-- calls a model through its provider interface
  |-- uses an MCP client
              |
         MCP messages
              |
      Financial MCP server
              |
      Existing Java statement services
              |
      Fixtures initially; EDGAR later

This is a proposed arrangement for our project. A server wrapping EdgarDataLoader can return financial data without making a model call. The host is where we later put the model-driven workflow. Spring AI supports both sides through its MCP integration.

A local Java tool can be useful without MCP. MCP becomes useful here when we expose that capability through a common interface to a separate client. Using MCP alone does not create an autonomous agent or a retrieval system.
