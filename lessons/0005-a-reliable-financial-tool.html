The concept: a tool is a contract

For this operation, the contract includes a name, a description, input fields, validation, a structured result, and failure behavior. Spring AI can turn an @Tool-annotated method into a ToolCallback. A description helps a model select the operation; application code must still enforce its rules. See Spring AI: Tool Calling.

JSON arguments
  → local Spring AI ToolCallback
  → getFinancialStatements(ticker, annualPeriods)
  → validate, normalize, create loader, load
  → FinancialStatements serialized as a tool result

No model selects the tool in this exercise. We supply the JSON ourselves to isolate conversion and execution. The callback is also not an MCP server; that protocol boundary comes next.

Checkpoint A: make the Java contract testable

Start with EdgarDataLoaderTool.java. It currently constructs three live SEC services inside the operation. Introduce a small factory boundary so a test can supply a loader returning fixed data.

Suggested interface shape
@FunctionalInterface
public interface FinancialDataLoaderFactory {
    FinancialDataLoader create(String ticker, int annualPeriods);
}

Put it in the loader package and inject an instance into the tool's constructor. Keep it as a plain Java interface. A test implementation can capture arguments and return () -> fixtureStatements. Do not introduce a Spring context just to test this method.

  1. Make the operation public for direct use outside its package.
  2. Reject null/blank tickers. Normalize accepted input with trim() and toUpperCase(Locale.ROOT) before delegation. Do not invent an alphabet-only ticker rule: punctuation may be meaningful.
  3. Choose an explicit period bound; use 1..4 for this exercise. Describe annualPeriods as the requested maximum number of recent annual periods, not a calendar year. The source may return fewer.
  4. Validate before invoking the factory. Return the loader's result without replacing missing metric values.
  5. Move SEC service construction to a production factory whose constructor receives the User-Agent. No model-supplied credentials or User-Agent arguments. External configuration wiring is deferred until a server/application actually uses this factory.

Keep the existing CLI working. Its direct construction of EdgarDataLoader need not change. This refactor concerns the wrapper; it does not require rewriting the statement services.

Prove behavior before adding AI annotations

Create ai-tooling/src/test/java/org/example/tools/EdgarDataLoaderToolTest.java. Use the existing JUnit/AssertJ dependencies and a hand-written factory or lambda. Build a small synthetic FinancialStatements fixture with source TEST_FIXTURE, periods 2024 and 2023, a reported value "0", and an unavailable value null. Do not represent it as real EDGAR data.

Checkpoint B: describe and invoke the same contract

Continue after A is working. Add org.springframework.ai:spring-ai-model:2.0.0 to ai-tooling/pom.xml: this matches the AI BOM currently used by chat-client. For this single dependency, an explicit version is enough; no model-provider starter or Boot migration is needed in tooling. The earlier lesson's 2.0.2 reference is not a reason to mix versions now.

In the tooling module's properties, enable maven.compiler.parameters=true so reflection can retain meaningful parameter names. Add @Tool to the operation and @ToolParam descriptions to its arguments.

Annotation imports and description checklist
import org.springframework.ai.tool.annotation.Tool;
import org.springframework.ai.tool.annotation.ToolParam;

Write the descriptions yourself. Include: annual statements; ticker input; period bound; fewer periods possible; formatted value strings; null for unavailable facts. A numeric description is not executable range validation. Keep the runtime checks from A.

Use ToolCallbacks.from(tool) in a local test to create the callback. Confirm the generated schema names ticker and annualPeriods and marks them required. Invoke it using valid JSON and parse its returned JSON to verify the original null and zero remain distinct.

Small callback inspection hint
import org.springframework.ai.support.ToolCallbacks;

var callbacks = ToolCallbacks.from(tool);
// Assert one callback, then inspect:
var definition = callbacks[0].getToolDefinition();
System.out.println(definition.name());
System.out.println(definition.inputSchema());

String json = callbacks[0].call(
        "{\"ticker\":\"AAPL\",\"annualPeriods\":2}");
// TODO: parse json and assert the fixture's zero/null values survived.

The API signatures were checked against the locally installed Spring AI 2.0.0 JAR. Your fixture factory makes this execution deterministic without a model or SEC request.

Add one callback test passing annualPeriods=5 and verify the factory is not invoked. The callback may wrap the validation exception; inspect its cause rather than assuming it is the exact exception type thrown by a direct Java call.

We keep failures explicit in these local tests. Translating expected failures into client-facing tool responses belongs to the later MCP/application adapter; do not catch every exception and return an empty success object.
